# MT-24 — Hook de git em camadas: fechar a indireção

**Contexto.** O hook `PreToolUse` entregue em `1be2af1` lê a linha de comando e é cego a
indireção. Verificado: **8 de 10** formas passam, entre elas `sh -c 'git commit'`,
`bash script.sh`, `/usr/bin/git commit`, `xargs -I{} git commit` e `eval "git push"`. Regex
fecha os oito vetores, não a classe — o espaço de indireção é aberto.

**Atualização de 2026-10-12 — a camada de texto foi medida e melhorada.** A ancoragem por
posição de `checar-comando-git.sh` dava a precisão (não recusa `grep -rn "git commit" docs/`,
pega `git -C . push`, espaço duplo, `cd /x && git commit`) e era exatamente o que abria a
indireção: nos vetores que passavam, o `git` vinha precedido de aspa, de barra ou de outro
programa. A guarda ganhou uma **segunda camada, gananciosa**: quebra a linha nos separadores
de comando e procura `git` + verbo mutante em qualquer posição de qualquer segmento, com
ressalva para segmento que começa por ferramenta de leitura. Medido depois:

```
RECUSOU: sh -c 'git push'  /usr/bin/git push  eval "git push"  env git push
         echo x | xargs -I{} git push  f(){ git push; }; f  ( cd /x && git reset --hard )
         echo `git commit`  echo $(git push)  git  push  git -C . push
passou:  git status  git log  git branch --show-current  grep -rn "git push" docs/
         rg "git commit" skills/  echo "nunca rode git push"  cd ~/x && git status
```

Autoteste: **25 recusas e 21 liberações**, todas corretas. O aprendizado do casamento sem
ancoragem veio de guarda de terceiro (Matt Pocock, `skills`, MIT,
github.com/mattpocock/skills), medida contra os mesmos vetores: ela fechava seis que nós
deixávamos passar e falhava nos cinco que nós pegávamos, além de bloquear leitura de
documentação e não cobrir `git commit`. Importamos o mecanismo, não o arquivo.

**O que isto NÃO fecha, e por que o ticket continua.** Indireção que **apaga o texto** do
comando: `bash ./deploy.sh`, `g=push; git $g`, `G=git; $G push`, `git pu"sh"`. Nenhuma camada
de texto fecha, e o autoteste agora **lista esses quatro casos como lacuna conhecida**, para
que "autoteste passou" não seja lido como "está coberto". Quem fecha é a camada 1.

**Escopo**

- **Camada 1, primária:** hook do próprio git (`pre-commit`, `pre-push`), que dispara em
  qualquer caminho de invocação. Nega por padrão quando a marca de sessão de agente está no
  ambiente; aprova só com token positivo prefixado por invocação, que o framework nunca
  exporta. A pessoa digita o token uma vez, consciente e auditável.
- **Camada 2:** `deny` do `PreToolUse` para os literais estreitos — o próprio token de escape,
  `--no-verify` e escrita em `core.hooksPath`. Sem isso o agente digita o token de escape e a
  camada 1 cai. Literal fixo é o que prefixo casa com confiabilidade. A guarda de texto em
  duas camadas já está entregue e testada (ver atualização acima); falta só o `deny` dos
  literais de escape.
- **Camada 3:** registrar cada recusa como evento do ledger (MT-22). A sonda de ataque vira
  telemetria.
- Instalação conferida pelo diagnóstico, e os dez vetores viram teste.

**Critério de aceite.** Os quatro vetores hoje listados como lacuna conhecida no autoteste de
`checar-comando-git.sh` passam a ser bloqueados pela camada 1, e saem da lista; `git` humano
com o token passa; o agente tentando o token é recusado pela camada 2; a recusa aparece no
ledger. O autoteste da camada de texto continua em 25/21 sem regressão.

**Fora de escopo.** Garantia completa. Está declarado no ticket: `--no-verify` pula hook local,
e fechamento real exige `pre-receive` no remoto.
